# TN Assistant API contract

## Origin, authentication and errors

The production client uses `https://assistant.tnfastvn.com` for dashboard, API and authenticated audio. JSON errors use `{ "error": { "code": "...", "message": "..." } }`. Protected routes require a TN Bearer access token. Access and refresh credentials are never embedded in the mobile package.

The client registers through `/v1/auth/register`, signs in through `/v1/auth/login`, rotates sessions through `/v1/auth/refresh`, and revokes the current family through `/v1/auth/logout`. Account ownership and device limits are enforced by the server. A client cannot grant itself admin or Premium access.

`GET /v1/me` returns effective `premium_features`: the server grants every TN Premium capability to accounts whose stored role is `admin`. Demotion takes effect on subsequent requests, including existing sessions. Other accounts retain the active entitlement policy. `local_premium` is an object with an `enabled` boolean, not a boolean field. Role rights do not create a purchase or grant access to paid upstream services; provider readiness remains separate. Android shows Premium and omits upgrade prompts for an authenticated TN Admin.

## Assistant and device actions

`POST /v1/assistant/text` accepts a text command, request ID, optional device ID, and optional permissioned coordinates. The server normalizes local command intents before using an optional AI profile. Commands without a verified data source return an explicit unavailable result.

Each executable directive has a server-issued action ID. The Android client reports `success`, `failed`, `unsupported`, or `cancelled` to `/v1/device/actions/results` with the request and action IDs. “Success” describes only the operation the OS confirms; launching a map intent does not prove arrival or route completion. Unsupported media, OEM or vehicle actions must remain unsupported until a real handler and device test exist.

Explicit Basic “open YouTube”, YouTube search, and “open link” commands return a `YouTube` directive. Its payload accepts `query`, `youtube_search`, `video_id`, or `direct_link`; direct HTTPS links take precedence, followed by an explicit YouTube search, a validated 11-character video ID, then a results-page search fallback. Android tries the configured `video_package`, the YouTube app, and the system HTTPS handler, and reports only whether an intent started. Search/parser API calls, automatic video selection, and playback completion are not claimed.

The `.178` Android source uses one ordered TN executor for foreground and wake actions. `PlayerVolume` controls `STREAM_MUSIC`: relative commands use the original 15-percent step, while `adjust_level` uses ten steps and `adjust_percentage` uses percent, with the unused field set to `-1`. The receipt records the requested and observed volume, and succeeds only when the observed value matches. Normal Android audio-settings permission is declared. `Delay` is bounded to 30 seconds and cancellation interrupts the wait. A prerequisite is an earlier `action_id|result`; unmet prerequisites are reported cancelled. Duplicate action IDs within a response and replayed responses are not re-executed. A receipt transport failure stops the remaining batch.

`PlayerMP3` transport is routed through that same executor. Exact Vietnamese imperatives produce `music_control_next`, `music_control_prev`, `music_control_resume`, `music_control_replay` or `music_control_stop` in `payload.command`; STOP means pause, retaining the track position, matching the original media service. Android needs explicit notification-listener access and uses the first priority active MediaSession, never another player as an automatic fallback. The selected player must advertise the specific action (previous also requires seek). Next/previous require observed track/queue change; resume/pause require the requested playback state; replay requires a reset position on the same identifiable track. After dispatch, the matching usable state and track/queue identity must remain stable for at least 100 ms, since metadata and playback state arrive independently. Confirmation is bounded to 2.5 seconds with owner/cancellation checks, no automatic dispatch retry. Error state, vanished session, revoked permission and unconfirmed results are failures. Track identity is compared in memory and excluded from receipts. These controls do not implement music search, favourites, subscriptions or a provider-account API; Android SDK session tests do not prove partner playback or acoustic recognition.

Actions are scoped to the login generation. Access-token rotation preserves the generation; logout, another login or external removal of persisted session state retires it. Delayed UI launches, speech and receipts must not run for a retired owner. Session refresh performs its network I/O outside the session monitor, so logout or account replacement can proceed while the network is slow; the old response cannot persist credentials afterward.

An unknown independent command is identified by `source=tn_command_router_fallback`. Commands-only mode retains its spoken unavailable reply. In `qa`/`tools`, it is unhandled and may proceed to the authorized AI route, subject to existing Premium, provider, free-tier and quota checks. This does not enable a provider or override the caller's selected mode.

Foreground and wake Android requests omit `mode`. The server resolves the saved account preference: Basic remains commands-only; Premium/Admin use their authorized preference or default QA. Both Android entry points use an opaque process-local `conversation_id`, maintained across token refresh and consecutive turns, expired after 30 minutes of inactivity, and replaced for another login generation or device. Logout retires the current owner's context; stale work cannot replace a new owner's context. No transcript, provider session key or credential is stored in this client context. Request IDs remain unique per turn and unchanged during an authentication retry.

The wake HTTP client reads at most 8 KiB from an error response and maps known TN codes to local messages. Missing AI configuration, unverified free tier, rejected credentials, quota, timeout and unavailable live data remain distinct; provider errors do not revoke a TN session. A feature-denied 403 is not represented as an expired login. Raw provider messages are not echoed by this client. The visible app uses the same known AI-code translations.

The validated AI `navigate` tool includes both the destination `query` and an HTTPS Google Maps `/maps/dir/` URL accepted by the active Android handlers. The destination is encoded as a single query value; it cannot change the target host or inject additional URL parameters. Launch acknowledgement remains evidence of opening the map only.

Sensitive tools return `confirmation_required=true`, `confirmation_token`, and `confirmation={type,summary,expires_in_ms}`. Summary and spoken consent text are derived from validated immutable arguments; they do not repeat model claims of execution. Tokens are bound to account, device, conversation and (in independent runtime) runtime generation, expire after two minutes, and are atomically consumed once. A different request ID cannot redeem the same token twice. The approved request uses `mode=tools`, the original conversation ID, a new request ID and the token; current account permissions are checked again. A retired generation or expired token cannot emit the directive.

Android holds the current proposal in RAM only and shows an explicit two-button consent dialog using the existing reference dialog styling. Pending consent allows only speech directives, never device actions. New turns, account changes, expiry, cancel/Back, leaving the foreground or destroying the Activity invalidate visible consent. A wake proposal received in the background may be shown when the owner returns before expiry; no automatic consent or background launch occurs. The dialog pauses wake capture while open. Confirmation clicks are one-use and recheck login/turn ownership; a late, duplicate or retired click cannot submit. Completing consent is not completion of the device action; the Android adapter must still validate permissions, ownership and its actual dispatch or persisted state. Unimplemented action subtypes report unsupported. Preview fields are additive and require a matching server/client release; an old server without the validated preview is rejected rather than guessing an action from model text.

The active Android `Alerts` adapter supports `Alarm`, `Timer`, `ShowAlarms` and (Android 6+) `DismissAlarm` through the public Clock intents. It declares the normal SET_ALARM permission and package-visibility queries. Alarm fields must be integral, date/time valid, and repeat one of None/Daily/Weekly/Weekdays/Weekend; timers accept 1..86400 seconds. AlarmClock has no absolute-date extra, so a date that is not the next representable local occurrence is rejected rather than silently scheduled earlier. Dismiss-by-time includes an explicit AM/PM selection; dismiss never requests skipping the Clock confirmation UI. A successful Clock dispatch receipt records `intent_started=true`, `completion_verified=false` and `interaction_required=true`; Android asks the user to check the target application rather than saying an alarm was created. Launching Clock may pause TN without retiring the approved owner's receipt channel. Actual persistence is verified separately in the isolated AVD test, never inferred from dispatch.

The independent Android `PhoneCall` adapter handles the server-issued, confirmed `payload.phone_number` through public ACTION_CALL with a tel URI. The value must be a string matching `\+?[0-9]{3,15}`; URI control characters, USSD/MMI sequences and non-string inputs cannot be forwarded. The manifest declares CALL_PHONE, optional telephony hardware and the corresponding visibility query. Foreground may request CALL_PHONE in context; background cannot open a permission dialog. The shared action-permission coordinator binds callbacks to request code and the exact requested permission set, ignores callbacks for another action, prevents an abandoned queued prompt from appearing and waits for Activity resume after a grant. The foreground call launch checks visibility again on the main thread immediately before dispatch; hiding the app cannot leave a delayed call launch. Permission denial, unavailable handler and changed ownership never claim a dispatched call. There is no automatic retry or substitution with ACTION_DIAL. A dispatch receipt reports `intent_started=true`, `completion_verified=false`, `interaction_required=true`, reason `call_request_dispatched`; it contains no phone number and does not claim connection, answer or call completion. SDK AVD tests separately cover the actual grant UI, intercepted dispatch/cancellation, and Android Telecom dispatch into the named AVD's virtual modem, followed by hangup and deletion of only its QA call-log row. Contact lookup/name disambiguation, Basic phone-command routing and voice-to-call acceptance remain open.

`Alerts` with `payload.type=Reminder` uses the independent TN Calendar Provider adapter in the same foreground/wake executor. A confirmed command needs READ_CALENDAR and WRITE_CALENDAR; foreground can request those permissions, while background execution cannot open a permission prompt. Denial, cancellation, invalid date/title/recurrence, missing writable calendar or lack of alert support fails explicitly without claiming storage. Permission requests abandoned while queued must not display later, and a late callback remains associated with its original command. Android selects the first visible, syncing, writable calendar supporting an alert, preferring primary calendars; it does not invent calendar ID 1 or create a user calendar. Task titles accept at most 200 Unicode code points. The event lasts one hour; recurring events use RRULE plus DURATION as required by the [Calendar Provider contract](https://developer.android.com/identity/providers/calendar-provider). Event and reminder inserts use one atomic batch. Success requires read-back of both records and reports `calendar_event_saved=true`, `completion_verified=true` with reason `calendar_event_and_reminder_verified`, without storing the event title in receipt details. This verifies persistence, not eventual notification delivery. Cancellation after the batch attempts to remove that event. The original application's 10,000-minute reminder lead is retained pending the owner's choice; it is not silently changed to zero. SDK AVD tests cover actual Calendar persistence, recurrence, rejected-batch rollback, owner cancellation and foreground wiring, not cloud inference or spoken-command end-to-end acceptance.

Private requests retain only opaque server-issued action IDs for receipt authorization, separate from redacted/evicted answer bodies. Receipts must still match account, device and runtime generation. A private originating turn remains private even if the setting is disabled before its receipt; enabling privacy before a late receipt also redacts its details. Private receipt storage contains only request/action IDs, result and a full-body fingerprint for duplicate/conflict checks, never arbitrary `details`. Existing pre-migration requests whose answer and action IDs were already removed are not reconstructed from client assertions.

Privacy is latched for accepted in-flight requests when enabled, including an on/off toggle before generation completes. AI conversation context is staged only in memory, then saved atomically with final history and replay state after privacy is checked again in that transaction. A private turn keeps its delivered answer available to the caller but does not persist that question/answer in context, history or replay body. Failure to commit final history rolls back context too. This controls TN persistence; a setting change cannot recall a request already sent to a provider.

`POST /v1/device/events` accepts TN-owned telemetry with a unique event ID and occurrence time. Events and action results are isolated by authenticated account and registered device. Replayed request/action IDs must not execute again.

When the account's current `private_mode` is enabled, a device event is accepted with only its event ID, kind and occurrence time retained as an idempotency tombstone. Its `data` and any payload-derived fingerprint are discarded. This applies to late retries as well; it does not retroactively erase events stored before private mode was enabled.

The independent Android client may send `app_opened` and `app_activated` events with a fixed `data.activation_source` category (`launcher`, `shortcut`, `wake_word`, `touch_screen`, `floating_assistant`, `floating_plan`, `floating_traffic`, `deep_link` or `external`). It does not send arbitrary intent extras, command text or URL data as activation telemetry.

## Voice, weather and sources

A visible microphone tap is explicit activation and does not require saying the wake phrase first. Its capture uses independent VAD and stops when the Activity leaves the foreground. A leading TN wake phrase is optional and may be stripped from the resulting transcript. Background wake listening remains a separate opt-in foreground service; it requires an acoustic wake and retains the confirmed-prefix checks for that initial utterance. These contracts do not establish human acoustic accuracy or streaming acceptance.

`GET /v1/settings` and `PUT /v1/settings` expose the account-scoped `agent_voice` preference. PUT accepts only the exact strings `south` and `north`; an invalid value rejects the entire update with `400 INVALID_SETTINGS`. Omitting the field preserves an existing choice. Settings responses display `south` when no valid choice has been saved. Reading settings or updating another field does not save that response default as an explicit choice.

In independent runtime with `TN_TTS_PROVIDER=original`, `POST /v1/tts` signs synthesis with speaker `5` for saved `south`, or `11` for saved `north`. A missing or invalid saved choice retains the operator-configured provider speaker, even when settings display the Southern response default. Request-level `speaker_id` or `agent_voice` fields cannot override the authenticated account's choice. This does not change shared provider configuration, other TTS providers, or managed-news voice selection.

`POST /v1/speech/decode` accepts raw mono PCM16 at 16 kHz for at most 15 seconds. The server may return only worker-produced recognition. WebSocket `ready/partial/final/end/cancel` messages must reflect actual incremental recognition; batch decoding is not streaming partial output.

`GET /v1/weather/current?lat=...&lon=...` requires exactly one valid latitude and longitude. The server truncates coordinates to four decimal places, calls MET Norway with an identifying User-Agent, observes cache headers and returns source, attribution, license, retrieval time and expiry. A weather command requires a recent location the user has permitted; no default or inferred location is substituted.

Traffic, camera and fine data must include source and update time. Missing or unverified records must not be presented as facts. News text and generated audio require rights confirmation; only TN-owned or cleared content may be published.

### Basic Clock and Calendar commands — API185 / Android194 candidate

This candidate is not yet the public backend release. Independent mode recognizes explicit timer, alarm, reminder, alarm-list and dismiss commands locally. Examples include `đặt hẹn giờ năm phút`, `đặt báo thức lúc bảy giờ sáng`, `nhắc tôi kiểm tra lịch lúc bảy giờ sáng` and `tắt báo thức tiếp theo`. Complete cardinal number groups, `HH:MM`/`7h30`, named day periods, today/tomorrow and None/Daily/Weekly/Weekdays/Weekend schedules are supported by the constrained grammar. Unrecognized or compound utterances stay with the existing NLU/fallback; this is not unrestricted Vietnamese language understanding.

Android194 adds `timezone` (the device's IANA or `GMT±HH:MM` identifier) and `client_capabilities: {"basic_alerts":true}` to assistant requests. Both fields participate in request replay identity when supplied. Old requests without either field retain the previous fingerprint shape. Missing timezone uses Vietnam time for older callers; invalid supplied zones fail with `INVALID_TIMEZONE`, never VPS local time. The date is the next future representable local occurrence. Clock cannot encode an arbitrary calendar date: incompatible explicit dates return an explanation without a device action. Calendar reminders may target tomorrow independently of Clock's next-occurrence limitation. Nonexistent DST wall times are not silently normalized.

Timer/alarm/reminder/dismiss mutations require the existing account/device/conversation/runtime-bound, expiring, one-use confirmation with `mode=commands`; this grants no AI or Premium rights and needs no provider call. The immutable proposal carries date fields plus `timezone`/`utc_offset_seconds` where relevant. Android validates the timezone and offset again before creating an intent or calendar write. Changed zones with different future DST rules are rejected even if their current offsets match. Legacy metadata with neither field retains existing adapter validation. Clients without the Basic Alerts capability receive an update instruction for mutations; alarm listing remains read-only and available. A supplied request-body device ID cannot replace authenticated device binding.

Original Clock intent behavior remains in the adapters. A successful dispatch still does not prove alarm persistence or eventual ringing. Calendar's historical `ORIGINAL_REMINDER_MINUTES=10000` remains unchanged for parity; actual reminder delivery and the broader human/partner/hardware journeys are not accepted by parser or staging tests. The new backend must pass isolated staging acceptance and the existing production promotion gates before going live.

### Basic contact calls — candidate .179

The independent command router accepts only explicit `gọi cho <name>` and `gọi điện cho <name>` imperatives as `PhoneCall.payload.contact_name`; it uses the same one-use account/device/conversation/runtime-bound confirmation as number dialing and does not send the contact name to AI. The Android client queries the local Contacts Provider only after confirmation and READ_CONTACTS consent, requires an exact normalized full display-name match, and separately obtains CALL_PHONE before ACTION_CALL. Foreground users choose among multiple numbers from a dialog that shows the contact/type and masked final digits. Wake can proceed only with one exact number and an already granted contacts permission; it never guesses among multiple matches. Receipts exclude both name and number. Candidate `.179` passed one scoped Android SDK AVD API 30 instrumentation test: exact lookup produced an intercepted ACTION_CALL, ambiguous results without a chooser were rejected, and the chooser callback selected the requested number. The test never dispatched a real call; it did not exercise the visible MainActivity dialog or speech-to-call end-to-end.

## AI, billing and providers

Gemini keys are write-only encrypted provider credentials; never send them to the mobile client. Free-only mode has no paid fallback, no automatic billing enablement and no search grounding. Rate limits belong to the Google project, not individual API keys. Only enable inference after a live request verifies project, quota and model.

Payment remains sandbox. Zalo is optional account linking; its registered HTTPS callback must match the provider configuration. Test fixtures prove protocol handling only, not acceptance by Zalo or an upstream service.

## Readiness and rollout

`/v1/health` is a process liveness check. Runtime readiness and capability output distinguish configured, untested, unavailable and ready features. A UI label or passing fixture cannot upgrade a capability to ready. Production enablement requires a real source or device test for that capability.

The explicit `TN_TTS_PROVIDER=original` selection is a TTS-only external dependency. It leaves the TN command/account runtime and Deepgram ASR unchanged. `/v1/tts` returns an ownership-protected, same-origin audio URL with `mime_type=audio/mpeg`; signed upstream URLs and credentials are never returned. Readiness identifies `original_tts`, its speaker ID and an external dependency, requiring valid synthesis for the current configuration within 24 hours. Managed news preserves existing WAV files and can generate MP3 from the selected TTS provider. Service availability, quota and commercial terms for this original provider are separate from runtime readiness.


### Account-plan display

`GET /v1/me` also returns `account_plan` with `kind` (`basic`, `premium`, `admin`), nullable RFC3339 `expires_at`, and RFC3339 `server_time`. Admin is selected by the stored user role. Premium requires an active full-premium product or active local-admin grant; partial feature grants do not imply a full subscription. The snapshot is presentation data, never authorization. Android calculates remaining days with a ceiling from server time and refreshes the snapshot; role and capability checks remain on the server.
