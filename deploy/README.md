## Current runtime contract

Run production with `TN_RUNTIME_MODE=independent`, loopback bind `127.0.0.1:8094`, persistent data under `/var/lib/tn-assistant`, configuration under `/etc/tn-assistant`, binaries under `/srv/tn-assistant/releases`, and static dashboard files in the aaPanel webroot. Public traffic reaches the backend only through the existing HTTPS reverse proxy. The runtime tree is deliberately outside `/root` and separate from the aaPanel webroot.

The live aaPanel Nginx vhost document root was rechecked on 2026-11-09T19:40Z: `assistant.tnfastvn.com` serves `/www/wwwroot/tn.assistant`. `TN_STATIC_DIR` was separately checked against this directory on 2026-11-06. Keep static deployment output there; `/root` is not a website root. Both deployment entry points refuse any `WEB` path other than this confirmed aaPanel directory.

`tn-assistant.service` starts the backend and restarts it on failure. `tn-assistant-monitor.service` runs the bounded 24-hour health observation. The aaPanel cron task `TN Assistant readiness watch` runs `/srv/tn-assistant/ops/readiness_watch.py` every five minutes. It reads local and public health/readiness, writes the latest snapshot plus state transitions under `/var/lib/tn-assistant/ops`, and makes no provider calls. The snapshot separates `service_available` (local/public health) from `features_ready` (local/public readiness), while retaining the combined `ok` field. ASR and TTS workers use separate Python virtual environments and bind only to loopback. Install them from the checked-in ASR/TTS requirement lockfiles with `install_speech.py`.

The watcher also records `persistent_rootfs_identity_ok`: `/.fly-vps-rootfs-v1` must be a regular non-symlink file containing `fly-vps-rootfs-v1`. A change is included in the transition log. This field does not alter combined `ok`, recreate the marker, restart Fly or send alerts; an outer-bootstrap failure still requires provider-console recovery. [Scheduled production evidence](../reports/parity100/readiness_rootfs_guard_20261110.json).

Production can select server-side cloud speech instead of local models. `TN_ASR_PROVIDER=deepgram` keeps ASR on Deepgram. The operator-requested `TN_TTS_PROVIDER=original` exception uses only the original app's TTS endpoint, with private `TN_TTS_API_KEY` and `TN_TTS_SECRET` environment references in `providers.json`. It does not enable the old ASR/NLU/actions. Local model workers can remain disabled and their model files absent. This TTS selection depends on the original service; its availability, quota and commercial terms must be verified separately.

Original TTS requires mode `legacy_tn`, URL `https://partner-speech.lab.zalo.ai/tts/stream`, `api_key_env=TN_TTS_API_KEY`, `secret_env=TN_TTS_SECRET`, and options `speaker_id`, `app_src`, `encode_type=2`. Production retains speaker `5` from the existing app configuration. Keys stay out of source bundles and clients. The server signs the request, fetches only approved HTTPS playlist/chunk hosts without redirects, validates MP3 frames, and serves authenticated same-origin `audio/mpeg`. Synthesis allows 1..500 characters, two concurrent requests and a 45-second total deadline. News jobs retain WAV compatibility and store new original-TTS audio as MP3. Readiness requires successful synthesis within the last 24 hours for the current credential/configuration fingerprint.

Before any release, build and test from a clean source allowlist, run `package_release.py`, inspect both manifests, scan for secrets, verify SQLite integrity and keep a consistent backup plus its encryption key. Stage the candidate with separate database/configuration first. Do not switch the production symlink until readiness, reverse proxy, dashboard, authenticated API, worker inference and rollback have been checked.

For an already initialized independent runtime, `deploy_ui_release.py` performs an incremental release without changing the live database, environment, provider configuration, AI key or admin password. It makes a private database/config/key/dashboard backup, switches the backend with rollback, installs the packaged dashboard, verifies its files through the public HTTPS reverse proxy, and publishes the versioned APK only after those checks pass. It requires both `/v1/health` and the backend's `/v1/ready` to pass before and after switching; the dashboard fallback at `/readyz` is not a readiness check. It refuses unclassified webroot paths and restores the previous dashboard and backend if candidate verification fails. This incremental path does not replace the separate staging checks required above.

After switching, verify health, readiness, user data, TLS/ACME renewal and service restart behavior. A green process health check alone is not feature acceptance. Keep unsupported automation and unverified data sources disabled; do not substitute an external web page or fixture response.

## Backend-only release

`package_backend_source.py` creates a root-readable backend source archive with a file manifest for an already built Linux binary. The archive deliberately stays under `/srv/tn-assistant/staging`, never under the aaPanel webroot. It is not a public artifact. Its metadata records that a local private-content scan was not performed; the VPS promotion step checks live environment secret values against the unpacked source before copying it to `/srv/tn-assistant/source`.

`promote_backend_only.py` is the separate promotion path for an API-only change. Stage the binary, source archive and the three Python files `promote_backend_only.py`, `deploy_ui_release.py`, `deploy_remote.py` together under `/srv/tn-assistant/staging/<release>`. The script requires the existing 24-hour monitor to have completed with zero failed samples and sufficient sample coverage. It verifies SHA-256 and the current release identity, checks service/environment/database/webroot state, creates a consistent SQLite and private-config backup, switches the release symlink, then verifies local and public health/readiness, the process executable, protected data and unchanged dashboard. A failed candidate restores the previous executable symlink and service; the live database is never overwritten during rollback. The script neither installs dashboard files nor publishes an APK.

Promotion also requires a root-controlled `STAGING_ACCEPTANCE.json` in the stage directory, recorded within six hours for the exact binary and source hashes. It must show `status=passed`, `isolated_database=true`, `health_status=ok`, `readiness_status=ready` and `external_provider_calls=0`. `accept_backend_staging.py` creates a private SQLite copy, neutralizes queued news work in that copy, runs the candidate as `tnstage` on port 18094 under systemd `PrivateNetwork=yes`, checks that only loopback is available and that an external route returns `ENETUNREACH`, then removes the private copy after stopping the candidate. `refresh_provider_readiness.py` makes one short Original TTS and Deepgram inference through a disposable guest when explicitly authorized; it removes the guest and prints no token, audio or transcript. It is a manual tool, not a scheduled quota consumer.
